# みらいぎかいっち＠大分市　議事録更新手順書

作成日：2026年10月11日

> [!IMPORTANT]
> この手順書は「大分市議会ホームページに議事録が公開されたとき」に使います。
> 1ステップずつ確認・承認してから次に進んでください。一気にやらないこと。

---

## 全体の流れ

```
STEP 1  議事録テキストを用意する
STEP 2  AIに4つのコンテンツを生成させる（1つずつ）
STEP 3  内容を確認・承認する
STEP 4  Supabaseに登録する（承認後のみ）
STEP 5  勝手に本番公開させないための確認手順
STEP 6  公開後の確認
```

---

## STEP 1：議事録テキストを用意する

大分市議会ホームページから議事録をコピーして手元に用意する。

**確認ポイント：**
- 会期名（例：令和8年第4回定例会）
- 会議名（例：本会議 / 総務常任委員会）
- 開催日（例：2026年11月30日）
- 議事録の全文テキスト（または主要部分）

---


## STEP 2：AIへの依頼プロンプト（4種類）

> [!IMPORTANT]
> **【重要】作成する3つのコンテンツの住み分けについて**
> （ここに先ほどの3つの住み分けルールを書く）

以下のプロンプトを1つずつ使う。

**各ステップで出力内容を確認・承認してから次に進むこと。**
> [!IMPORTANT]
> **【重要】作成する3つのコンテンツの住み分けについて**
> AIに作業を指示する際は、以下の違いと役割を厳守させること（役割を混同させない）。
> 
> 1. **議事録要約（/committees）**
>    - **役割：** 議事録そのものをわかりやすく整理・要約するページ。
>    - **対象：** 会議全体の流れや、そこで決まったこと、出席者など。
> 2. **議案詳細（/committees/bill-pickups/[id]）**
>    - **役割：** 個別の議案や請願などをピックアップして詳細に紹介するページ。
>    - **対象：** 1つの議案の概要や、市民生活への影響、審議の流れ。
> 3. **トピックス記事（/topics）**
>    - **役割：** 議事録全体から読み解き、市民が身近に感じる話題を**複数の議案などを跨ってもよい**分かりやすい解説記事として紹介するページ。
>    - **対象：** 住民が興味を持つテーマ別の深掘り記事、大分弁の感想など。

### 2-A　トピックス記事の作成

**用途：** サイトの `/topics` ページに表示する住民向け解説記事

**AIへのプロンプト（コピーして使う）：**

```
以下の議事録をもとに、「みらいぎかいっち＠大分市」サイト用のトピックス記事を作成してください。

【会期・会議名】
（ここに入力：例「令和8年第4回定例会 本会議（2026年11月30日）」）

【議事録テキスト】
（ここに議事録を貼り付け）

【出力してほしい内容】
以下の形式でMarkdownで出力してください：

## タイトル
（住民が興味を持つ、わかりやすい見出し。30文字以内）

## カテゴリ
（以下から1つ選択：子育て・教育 / 安心・安全・防災 / まちづくり・暮らし / まちの仕組み・選挙）

## 要約（3行）
- 1行目：（この議案・審議で何が決まったか。1文）
- 2行目：（市民生活への影響・変化。1文）
- 3行目：（今後のスケジュールや注意点。1文）

## 詳細
（経緯・質疑の流れを含む、300〜500文字の解説文）

## 理由・背景
（なぜこの議案が提案されたか、行政側の意図。200文字以内）

## ポイント3つ
- ポイント1：
- ポイント2：
- ポイント3：

## 対象者
（この決定が直接影響する市民の層）

## 賛成の声（大分弁で）
（市民が期待しそうな肯定的な声を1〜2文。「〜やな」「〜やけん」等の大分弁で）

## 慎重・懸念の声（大分弁で）
（市民が心配しそうな声を1〜2文。大分弁で）

## 関連する会議・議案（source_refs用）
- 会議名：（例：令和8年第4回定例会 本会議 第1日目）
- 議案番号：（例：第101号）
- 議案名：（例：○○条例の一部改正について）

【注意事項】
- 中国語の漢字（议、务、该 等）を使わないこと
- 語尾・文体を統一すること（「〜した」「〜された」等）
- 情報は議事録の内容に忠実に。創作しないこと
- **【トピックスと議案詳細のリンク】**:
  - `bill_articles` テーブルの `source_refs` カラムに上記の会議・議案情報を登録することで、トピックス詳細のアコーディオンに関連議案のリンクが自動表示されます ✅
```

**登録先テーブル：** `bill_articles`（billsテーブルの議案IDと紐付けて登録）

### 2-B　本会議・委員会の要約作成

**用途：** `/committees` ページに表示する会議の概要

**AIへのプロンプト（コピーして使う）：**

```
以下の議事録をもとに、会議の要約データを作成してください。

【会期・会議名】
（ここに入力）

【開催日】
（ここに入力：例「2026年11月30日」）

【議事録テキスト】
（ここに貼り付け）

【出力してほしい内容（JSON形式）】

{
  "meeting": {
    "title": "（例：令和8年第4回定例会）",
    "meeting_type": "（「本会議」または「委員会」のどちらか）",
    "date": "（YYYY-MM-DD形式）",
    "term": "（例：R8第4回）"
  },
  "session": {
    "session_title": "（例：本会議 第1日目）",
    "date": "（YYYY-MM-DD形式）",
    "summary": "（会議全体の概要。200文字以内）",
    "decisions": "（この日に決定・可決・否決されたことの一覧。箇条書き）",
    "detailed_summary": "（審議の流れ・主な質疑応答を含む詳細要約。500文字程度）",
    "attendees": {
      "chair": "（議長名）",
      "vice_chair": "（副議長名）",
      "members": ["出席議員名の配列"],
      "absent": ["欠席議員名の配列（いなければ空配列）"],
      "officials": ["出席した行政職員・役職の配列"]
    },
    "bills": [
      {
        "number": "（議案番号：例「第101号」）",
        "name": "（議案・条例名）",
        "description": "（議案の内容を1〜2文で）",
        "result": "（「可決」「否決」「継続審査」のいずれか）",
        "billId": "（任意：STEP 2-Cで登録したbillsのUUID。空/nullでも番号・名前が一致していれば自動照合されてリンクが繋がります）"
      }
    ]
  }
}

【注意事項】
- 中国語漢字不使用
- 議事録に記載のない情報を創作しないこと
- 「bills」は審議された議案を全て列挙すること
- **【リンクが繋がる仕組み】**:
  - `bills` テーブルに登録した議案（STEP 2-C）と、ここの `number`（議案番号）または `name`（議案名）が一致し、`publish_status = 'published'` になっていれば、システムが自動照合して会議要約ページの議案名が議案詳細へのリンクになります ✅
  - もし即座に100%確実にリンクさせたい場合は、`billId` に直接 bills の UUID を設定してもOKです。
```

**登録先テーブル：** `meetings`（meeting）と `meeting_sessions`（session）

### 2-C　承認済み議案詳細データの作成

**用途：** `/committees/bill-pickups/[id]` ページに表示する議案詳細の本文

> [!NOTE]
> このページは `/bills/[id]`（AIインタビューあり）とは**別**です。混同しないこと。
> 議案詳細ページの本文は **`bill_contents`** テーブルです。`bill_articles`（トピックス用）とは別物です。

**AIへのプロンプト（コピーして使う）：**

```
以下の議案情報をもとに、承認済み議案の詳細ページ用データを作成してください。

【議案名】
（ここに入力）

【議案番号】
（ここに入力：例「第101号」）

【議決結果】
（例：可決 / 否決）

【議決日】
（例：2026年11月30日）

【議事録・関連資料テキスト】
（ここに貼り付け）

【出力してほしい内容（JSON形式）】

{
  "bill": {
    "name": "（条例・議案の正式名称）",
    "bill_number": "（議案番号：例「第101号」または「101」）",
    "headline": "（住民向けのキャッチコピー。30文字以内）",
    "description": "（議案の概要。100文字以内）",
    "status": "（「enacted」=可決成立 / 「rejected」=否決 のいずれか）",
    "publish_status": "published",
    "published_at": "（ISO8601形式：例「2026-11-30T00:00:00+09:00」）"
  },
  "bill_content": {
    "difficulty_level": "normal",
    "title": "（住民向けのわかりやすいタイトル。例：「○○条例が可決されました」）",
    "summary": "（3〜5文の要約。何が決まり市民生活にどう影響するかを平易な言葉で）",
    "content": "（以下の構成でMarkdown形式で書くこと）\n\n## この議案について\n（議案の概要と提案の背景）\n\n## 主な内容\n（条例・予算の具体的な内容。箇条書きも可）\n\n## 議会での審議\n（質疑応答・賛否の流れ）\n\n## 市民生活への影響\n（誰にどんな影響があるか）"
  }
}

【注意事項】
- 中国語漢字不使用
- 事実に基づいて作成。議事録にない情報を創作しないこと
- statusは必ず英語キーワードを使うこと（enacted / rejected）
- **publish_status は必ず `"published"` にすること**（これがないと非公開扱いとなり、会議一覧からのリンクも無効になります）
- **bill_number と name は会議要約（2-B）と完全一致させること**（一致していれば会議要約から議案詳細へ自動リンクされます）
- contentはMarkdown形式。見出し（##）・箇条書き（-）を使ってよい
- summaryは住民がパッと見てわかる平易な文章で
```

**登録先テーブル：** `bills`（bill） と `bill_contents`（bill_content）
- `bills` を先に登録してUUIDを取得し、そのIDで `bill_contents` を登録する
- `bill_contents` は同じ `bill_id` に `difficulty_level = normal` で1件登録

## STEP 3：生成内容の確認チェックリスト

AIが出力したら、登録前に必ず以下を確認すること：


- [ ] 中国語漢字が混入していないか（议、务、该 等）
- [ ] 語尾・文体が統一されているか
- [ ] 議事録の内容と整合しているか（創作・混入がないか）
- [ ] 複数の議案を処理した場合、議案Aの情報が議案Bに混入していないか
- [ ] 大分弁が不自然でないか
- [ ] 日付・議案番号が正確か

## STEP 4：Supabaseへの登録

> [!CAUTION]
> 承認なしに登録しないこと。AIが生成したデータは必ず確認後に登録する。

### 登録順序

```
1. bills テーブルに議案を登録（ID取得のため最初に行う）
2. bill_articles テーブルに記事を登録（bills.idが必要）
3. meetings テーブルに会議を登録（IDのため先に）
4. meeting_sessions テーブルに要約を登録
5. site_information テーブルにお知らせを登録
```

### 接続先の確認（毎回必須）

```
Supabaseプロジェクト名：みらいぎかいっち
Project ref：ombopirqedzbhuqpsvkw
```

接続前に `.env.production` のSUPABASE_URLを確認し、
`ombopirqedzbhuqpsvkw` が含まれていることを目視確認すること。
値そのものをチャットやファイルに出力・コピーしない。

### 登録後の確認


- `site_information` は `is_published = true` になっているか
- `bills` の `published_at` の日本時間が正しいか
- `meeting_sessions` の `bills` フィールドに全議案が入っているか
- 重複登録していないか（同じ議案を2回INSERTしない）

## STEP 5：勝手に本番公開させないための確認手順

> [!IMPORTANT]
> 何も対策しないとプッシュ時に勝手に本番が更新されるため、必ず以下の手順を守る。


1. **本番ブランチ（main等）に直接データを送らない**
   - パソコンから作業するときは、必ず別の名前の枝（ブランチ）を作ってからデータを送る（または、Vercelの自動デプロイ設定をOFFにする）。
2. **プレビュー画面で確認する**
   - データを送るとVercelが「確認用の専用URL」を作るので、まずはそこで画面が崩れていないか自分の目で見る。
3. **確認できてから本番に反映する**
   - よし！となてから、VercelまたはGitHubの画面で本番への反映ボタンを押す。

## STEP 6：公開後の確認

ログインしていない状態（プライベートウィンドウ）で以下を確認：

- [ ] スマホ表示でも崩れていないか

## よくある間違い

| 間違い | 正しい対応 |
|--------|-----------|
| `/bills/[id]` と `/committees/bill-pickups/[id]` を混同 | bill-pickupsが承認済み議案詳細、billsはAIインタビューページ |
| お知らせを重複INSERT | site_informationを確認してから登録 |
| 途中保存版のコミットを使ってビルド | 必ず完成版コミット `dda1110` 以降を使う |
| Production Branchを確認しないでデプロイ | Vercelの設定が旧ブランチのままの可能性あり（引き継ぎ書参照） |
| DB変更なしでSITE_INFORMATION_ENABLED変更後に再ビルドを忘れる | 環境変数変更後は必ず再ビルド |
