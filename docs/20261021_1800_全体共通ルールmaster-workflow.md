# みらいぎかいっち＠大分市：全体共通ルール（master-workflow.md）

本書は、「みらいぎかいっち＠大分市」のサイト運用において、議事録のデータをもとにコンテンツを作成・更新する際の最上位の共通ルールおよび全体設計図である。すべての作業（エージェントへの指示やデータ更新）は、本ルールの構造と制約に従うこと。

---

## 1. サイトの基本原則と目的
- 「みらいぎかいっち＠大分市」は、大分市議会の情報を市民にわかりやすく届けるプラットフォームである。議会を身近に感じて貰うことを目的とする。
- 議事録要約・議案詳細・トピックス記事は目的が異なる。表示やDBでは相互に参照する部分があるため、同じものとして扱わない。

---

## 2. サイト全体構造マップ（表と裏の対応関係）
作業時は、現在どのページ（表）を対象にし、どのデータベース（裏）を操作しているかを必ず区別・意識すること。混同は厳禁とする。

### ① 議事録要約
- **【表側】場所・役割:** `/committees` は本会議・委員会・議案一覧への入口。各開催日の詳細ページに要約、決定事項、議案、出席議員、議事録を表示する。
- **【裏側】データベース:** `meetings` は会議の基本情報、`meeting_sessions` は開催日ごとの原文・要約・決定事項・出席者・議案を持つ。
- **主なリンク:** 開催日の議案リストは、対応する公開済み議案を特定できた場合に議案詳細へリンクする。

### ② 議案詳細
- **【表側】場所・役割:** パス: `/committees/bill-pickups/[id]` （個別議案の深掘り解説、ステータス管理、背景・影響の解説）
- **【裏側】データベース:** テーブル: `bills`, `bill_contents`
- **主なリンク:** 出典となる会議の開催日ページにリンクする。公開済み議案と議事録中の議案が対応していることを確認する。

### ③ トピックス記事
- **【表側】場所・役割:** `/topics` に表示する、市民の暮らしに関わるテーマの解説記事。トップページには記事一覧への入口バナーが表示される。
- **【裏側】データベース:** 元データの `proposals` と表示用の `bill_articles` を参照する。現行の型定義では `bill_articles.bill_id` は数値の `proposals.id` を参照し、議案の `bills.id` ではない。作業時は対象環境のスキーマと既存データの対応を確認する。
- **主なリンク:** `bill_articles.source_refs` の会議・議案情報から会議ページを作る。議案詳細へのリンクは対応する公開済み議案を特定できた場合に表示されるため、登録後に実際のリンク先を確認する。

### ④ 議員プロフィールの「議会での発言」
- **【表側】場所・役割:** `/politicians/[id]` に、議員本人の議事録からの引用、見出し、必要に応じた補足、開催日別の議事録へのリンクを表示する。補足は原文の引用と区別して表示する。
- **【裏側】データベース:** `politician_speech_highlights` は議員、開催日、見出し、引用、補足、公開状態を持つ。議事録の原文は複製せず `meeting_sessions.content` を出典とし、公開ページには公開済みの発言のみ表示する。
- **選定:** 複数の会派を対象にする場合は偏りに注意し、対象の議事録・集計期間・発言量の目安を示す。機械集計は公式の発言回数とみなさず、発言者と前後の文脈を原文で確認する。見出しや補足が質問・提案を実施済みの事実に見せないようにする。
- **登録と更新:** 管理画面の「議員の発言」から議員・出典の開催日・見出し・原文の引用・任意の補足を入力する。引用は改行や空白も含めて原文どおりとし、リンク先で本人の発言と前後の文脈を確認する。下書き保存、編集、確認後の公開、非公開が可能。AIが作った見出し・補足は、下書き登録前にも内容と出典を提示して承認を得る。
- **出典更新時:** 議事録が変更されて引用が原文と一致しなくなると公開ページから非表示になり、確認できない発言がある旨を表示する。管理画面で元の議事録を開き、本人・文脈・引用を再確認してから編集・公開する。引用が同じでも発言者や文脈が変更された場合は、手動で非公開にして再確認する。
- **見本と公開の切替:** `POLITICIAN_SPEECH_MODE` が未設定なら機能は無効で、新テーブルを参照しない。`preview` はローカル開発または認証保護を確認した Vercel Preview でのみ、DB書き込みなしの見本を表示する。見本のJSONは公開リポジトリに含めず非公開で保管し、その内容を `POLITICIAN_SPEECH_PREVIEW_JSON` に設定する。PowerShell では `$env:POLITICIAN_SPEECH_PREVIEW_JSON = Get-Content -Raw -Encoding UTF8 '<見本JSONのパス>'` として、同じシェルで Web を起動する。`database` はマイグレーション適用後に Web と Admin で設定し、管理機能と公開済みデータの表示を有効にする。本番DBへのマイグレーション・下書き登録・一般公開は、それぞれ対象を示して別途承認を得る。
- **見本JSONの形式:** 配列の各要素は `id`、`politician_id`、`politician_name`、`meeting_session_id`、`meeting_id`、`meeting_type`（本会議または委員会）、`meeting_title`、`meeting_date`（YYYY-MM-DD）、`title`、`quote`、`context`（文字列または null）、`approved`（真偽値）を持つ。`id` と `politician_id` は UUID、`meeting_session_id` と `meeting_id` は数値とする。
- **見本の登録:** `node --env-file=.env.production scripts/apply-politician-speech-samples.mjs --file=<見本JSONのパス>` は議員・出典・引用・発言者の読み取り照合のみを行う。内容の承認後に対象の見本を `approved: true` とし、本番DB書き込みの承認と接続先確認、マイグレーション適用を済ませた場合のみ `--write` を付ける。未承認の見本がある場合は登録できず、新規登録は下書きになる。既存の編集済みデータは上書きしない。

> **※注意:** AIインタビュー（`/bills/[id]/interview`）や、トップページのお知らせ（`site_information`）は別の機能である。市長の提案理由・記者会見は [更新手順](20261101_2212_市長提案理由と記者会見の更新手順.md) を参照する。

### 【重要】`bills` テーブルの住み分け（`bills.source`）
AIインタビュー関連テーブル（`interview_configs` / `interview_sessions` / `interview_report` 等）はすべて `bills.id` を参照するため、トピックスのAIインタビュー用の「受け皿」も `bills` に入っている。テーブルは分けず、`source` カラムで区別する。

| `bills.source` | 中身 | 元データ | 表示先 | DBビュー |
|---|---|---|---|---|
| `meeting` | 議案（②） | 議事録 `meetings` | `/committees/bill-pickups`、議案一覧、`/bills/[id]`（議案のAIインタビュー） | `meeting_bills` |
| `topic` | トピックス（③）のAIインタビュー受け皿。**議案ではない** | `proposals` / `bill_articles` | 対応するトピックのAIインタビュー | `topic_interview_bills` |

- 議案を新規登録するときは `source = 'meeting'`（既定値）のままにする。
- トピックにAIインタビューを付けるため `bills` に行を作るときは **必ず `source = 'topic'`** にし、`bill_articles.interview_bill_id` にその `bills.id` を設定する（タイトル一致による推測は後方互換のためのフォールバックにすぎない）。
- アプリで議案を一覧・集計するときは `getMeetingBillFilter()` と `applyMeetingBillFilter()` を使う。`source` 列が未適用の環境では互換処理が必要なため、単純な `.eq("source", "meeting")` に置き換えない。DBを直接確認する場合も列やビューの適用状態を先に確認する。

## 3. 全体の基本ワークフローと鉄則
- **起点の作業（生データの格納）:**
  大分市の公式議事録と既存の会議・開催日を照合し、必要な原文を `meeting_sessions.content`、会議の基本情報を `meetings` に対応させる。既存レコードの削除・再投入やIDの推測はしない。
- **パーツごとに「1ステップずつ」進める（重要）:**
  一度にすべてのコンテンツをいっぺんに生成させず、必ず1つずつ（パーツごとに独立して）生成・確認・承認してから次のステップへ進むこと。
- **複数議案の混入防止:**
  複数の議案を扱うときは、情報の取り違えや混入が起きないよう議案ごとに分ける。同一の一般会計予算に複数のテーマがある場合は、正式な議案IDを維持し、必要に応じて見出し・サブタイトルでテーマを区別する。
- **過去情報・ステータス更新のチェック:**
  新着議事録を追加・更新する際は、必ず過去の関連情報（既存の議案詳細のステータス変化：「審議中」→「可決」などや、新しい続報）に影響がないかを確認し、必要に応じて過去ページも更新する。
- **内容・DB書き込み・公開の承認:**
  AIが生成・修正した全文と出典を提示して内容の承認を得る。本番DBへの書き込みと一般公開は、それぞれ対象・影響を示して別途承認を得る。下書き登録も本番DBへの書き込みに含む。
- **安全な公開プロセスとインフォメーション掲示:**
  プレビューと本番が同じDBを使う場合がある。プレビューで確認するためだけに共有DBへ先に書き込まず、接続先と公開条件を確認する。特に `meeting_sessions` に公開状態はなく、トピックスの下書きも設定によっては非表示にならない。
- **本番反映後の対応:**
  本番反映を確認した後、管理画面の「インフォメーション」から `site_information` のお知らせを掲載する。文案をAIが作る場合も承認後に登録する。`SITE_INFORMATION_ENABLED` 等の環境変数を変更した場合は、大分市版の現在の公開先と反映方法を確認する。

## 4. 全作業共通の安全・セキュリティ鉄則
- **Supabase接続時の目視確認:**
  [DB接続規約](../.claude/skills/db-access/SKILL.md) と現在の環境を照合し、使用する接続先が大分市版であることを確認する。他地域や古い接続先を前提とした記載はそのまま使用しない。URL・プロジェクト参照・認証情報を指示書に固定しない。
- **機密情報の保護:**
  機密情報や接続URLの値をチャットやファイルに誤って出力・コピーしないこと。
- **勝手な本番直撃の防止:**
  コード変更はworktree・PRで進め、サイトに反映する場合はプレビュー画面等で確認してから本番へデプロイする。DBを共有する場合の注意は上記の公開プロセスに従う。

---

## 5. 共通の禁止事項・注意事項
- **中国語漢字の排除:**
  中国語の漢字（`议`、`务`、`该` 等）は一切使用しないこと。
- **情報の正確性と創作の禁止:**
  情報は提供された議事録やデータベースの内容に忠実に従うこと（勝手に存在しない事実や発言を創作しない）。
- **アクセシビリティの意識:**
  専門用語をそのまま難解に並べるのではなく、市民がスッと理解できる表現を心がけること。

## 6. 【共通プロンプト】お知らせ（インフォメーション）文面の作成
本番反映完了後にお知らせを作成する際は、AIに以下のプロンプトを与えて文面を生成させること。

```markdown
以下の情報をもとに、サイトTOPのお知らせ文案だけを作成してください。登録・公開は私の確認後に行います。

【更新内容】
（例：「令和8年第4回定例会（11月30日〜12月14日）の情報を追加」）

【主な追加・変更内容】
（例：「本会議の要約、承認済み議案3件のトピックス記事」）

【お知らせ掲載日】
（例：2026年12月15日）

【出力してほしい内容】
- タイトル（30文字以内）：
- 本文（100文字以内）：

【注意事項】
- 市民にわかりやすい言葉で
- 「〜ました」の丁寧語
- 中国語漢字不使用
登録先テーブル： site_information
```

管理画面からタイトル・本文を登録する。現在のお知らせ本文はプレーンテキスト表示のため、URLを記載しても自動でクリックできるリンクにはならない。
