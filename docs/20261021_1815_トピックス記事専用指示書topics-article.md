# トピックス記事専用指示書（topics-article.md）

本書は、「みらいぎかいっち＠大分市」のトピックス記事（トピックスカード）を作成・更新する際の個別ルールおよびプロンプトの仕様を定めるものである。作業時は [全体共通ルール](20261021_1800_全体共通ルールmaster-workflow.md) を必ず遵守すること。

---

## 1. ページの基本仕様

### 【表側】サイト上の場所・役割
- **URLパス:** 記事カードは `/topics` に表示する。トップページには記事一覧への入口バナーを表示する。
- **役割:** 一つまたは複数の議案・会議を題材に、市民の暮らしに関わる話題を分かりやすく解説する読み物。議案そのものや会議全体の要約とは区別する。
- **題材の選び方:** 条例の変更点や可決内容を言い換えるだけの記事にしない。「暮らしのどんな困り事か」「なぜ今取り上げられたか」「市の説明や議会の指摘は何か」「何が解決し、何が課題として残るか」を原文から掘り下げる。議案説明と重なるだけで深掘りできない場合は題材を選び直す。報告事項・市民意見への回答・委員会協議も題材になるが、質疑がない会議に架空の議論を足さない。

### 【裏側】データベース構造
- **元データと表示:** 記事は `proposals` と `bill_articles` を参照する。現行の型定義では `bill_articles.bill_id` は `proposals.id` を参照する数値であり、議案の `bills.id` ではない。対象環境のスキーマと既存レコードを照合し、同名のIDを取り違えない。
- **表示値の優先:** 紐付く `proposals` に値がある場合、カテゴリ、審議状況、要約、詳細、理由、ポイント、対象者、賛成・慎重の声は、その値が `bill_articles` より優先される。片方だけを更新して表示が変わると決めつけず、両方と画面を確認する。
- **AIインタビューは全記事必須:** `bills` に **`source = 'topic'`** の行（インタビューの受け皿）を作り、その `bills.id` を `bill_articles.interview_bill_id` に設定する。受け皿は議案ではないため、議案一覧・議案詳細には表示されない（詳細は master-workflow.md「`bills` テーブルの住み分け」）。タイトル一致の推測に頼らず、記事ごとのIDで明示的に結ぶ。
- **AIインタビューの内容:** 記事の事実部分を `bill_contents` に、確認済みの出典・資料の時点・未確認事項を `interview_configs.knowledge_source` に設定し、テーマと事前質問・深掘り指針を作る。記事の想定の声を実在の意見や根拠資料として取り込まない。利用経験や賛否を決めつけず、個人情報の詳細を尋ねない。質問案も内容承認を受ける。公開時は受け皿の公開状態、設定の `status='public'`、記事からの導線、開始・応答を確認し、質問一覧のプレビューだけを「AI会話の動作確認済み」と扱わない。
- **公開状態:** Web側の `TOPIC_PUBLICATION_ENABLED=true` の場合のみ `publish_status='published'` を絞り込む。未設定・無効の場合、`draft` でも表示され得る。対象環境の設定とDBを確認し、共有DBに下書きを書けば安全だと考えない。DBの対応が済み管理画面側の同設定も有効な場合、トピックス管理で公開状態を操作できる。
- **審議状況との違い:** 記事に表示する「審議中」「予算可決」等は審議状況であり、記事の `draft` / `published` とは別である。

### 【リンク関係の仕組み】
- `bill_articles.source_refs` は会議ID・開催日ID・会議種別・会議名・日付・議案番号／名称・確認済み発言抜粋の配列。会議へのリンクはIDから組み立てられ、議案詳細へのリンクは公開済み議案と照合できた場合に表示される。IDや一致を推測せず、リンク先を確認する。
- 会議リンクの表示は **「厚生常任委員会・2026/3/24」などの会議名＋年月日** とする。日付だけでは何の会議か分からないため、`session_label` だけを表示しない。
- **外部の関連リンクと議事録リンクは別:** `link_url` / `link_label` にはテーマに合う大分市等の公式案内・資料を設定し、議事録は `source_refs` に残す。外部リンクは到達可否だけでなく、ページの内容・対象・時点も確認する。一般的な制度案内を特定の中止・決定の告知と誤認させず、PDFはリンク名に「PDF」と明記する。適切な公式ページを確認できなければ推測URLを作らず、その旨を伝える。

実装の確認先: [トピックスの取得処理](../web/src/features/bills/server/loaders/get-articles.ts)、[記事カードの表示](../web/src/features/bills/client/components/articles/article-accordion-card.tsx)。

## 2. ライティング・ガイドライン（トーン＆マナー）
- **文体:** 読者に語りかける、柔らかく誠実な丁寧語を使用する。
- **生活者目線:** 常に「この情報を知って、誰が・どう助かるのか？」という生活者目線を重視する。
- **賛成・慎重の声:** 記事の論点を踏まえた想定の声を、自然な大分弁のセリフ調で書く。AIが想定した声である旨は既存の「よくある質問」で説明する運用とし、各記事のセリフに「実際の発言ではありません」等の注記を重ねない。実在する市民・議員の名前を付けて架空の引用を作らず、出典のある実際の発言は原文を大分弁に改変しない。確認用資料では実発言と想定を区別し、裏付けのない論点を無理に作らない。
- **タイトルの統一フォーマット:** `[ステータス] + 【テーマ名】 + キャッチコピー` （※タイトルの文字数は全体で30文字以内を目安とする）。テーマ名は必要に応じ議案・条例名を使えるが、必ずしも正式な議案名を主題にしない。報告・協議を可決と書かない。画面には別途ステータスバッジも表示されるため、重複して読みにくくないか確認する。
- **情報の密度と品質（情報の省略禁止）:**
  - 議会や行政が公開している詳細情報を「省略」してはならない。特に行政的な背景や経緯（詳細・理由）は、情報が持つ「深さ」を削らずに正確に言語化すること（「情報は濃く、表現はやわらかく」を徹底）。
- **分量は記事全体で比較:** 「声」だけでなく、要約・詳細・背景・ポイント・対象者を含めて既存記事と同程度の文字数・情報量にする。既存の実表示値（`proposals` 優先）を確認し、文字数だけでなく具体性も比較する。2026年11月の確認では既存11記事の本文合計は約665〜922字、新規3記事は約1,000字が目安だったが、固定ノルマではない。根拠のない水増しや同じ説明の反復はしない。詳細300〜500字・背景200字以内の基準も守る。
- **段落と改行:** 詳細は話題の区切りで3〜4段落に分け、段落間に空行を入れる。ポイントは `【見出し】` の後で改行して説明を書く。既存記事が改行なしでも、長い新規本文を一段落に詰めない。実画面で読みやすさを確認する。
- **中国語漢字の排除:** `议`、`务`、`该` 等の中国語漢字は一切使用しないこと。

## 3. データベース / 項目定義（入力フォーマット）
トピックス記事として登録・出力する際は、以下の項目構造を厳守すること：

1. **タイトル:** `[ステータス] + 【テーマ名】 + キャッチコピー`
2. **ステータス:** 予算可決、審議中、議会提言、導入予定、試行中止の報告、協議 等。会議時点の実態に合わせる
3. **カテゴリ:** 以下から記事の主なカテゴリを1つ選択する。表示には `proposals.badge` が優先される。
   - **子育て・教育**（子ども、学校、給食、教育、子育て支援など）
   - **安心・安全・防災**（災害対策、避難、防犯、地域の安全、鳥獣対策など）
   - **まちづくり・暮らし**（空き家、移住、交通、住環境、地域交流など）
   - **まちの仕組み・選挙**（選挙、投票率、若者応援、議会改革、条例など）
4. **要約（3行）:**
   - 1行目：概要1行目（何が決まったか、または何が報告・協議されたか）
   - 2行目：概要2行目（市民生活への影響・変化）
   - 3行目：概要3行目（今後のスケジュールや注意点）
5. **詳細:** 経緯や本質的な内容（300〜500文字。3〜4段落に分けて空行を入れる）
6. **理由・背景:** 行政的な背景・意図（200文字以内）
7. **ポイント3つ:** 核心となる重要ポイントを3点漏らさず記述
`【ポイント】` の後に改行して詳細を書く
8. **対象者:** 制度・決定の対象者（影響を受ける市民の層）
9. **賛成の声:** 大分弁のセリフ調の想定例。AI生成の説明はFAQに統一する。
10. **慎重の声:** 同じく想定例。実在の人物の発言として扱わず、根拠のない論点を足さない。
11. **関連リンク:** 大分市等の公式外部案内・資料。議事録と分け、内容が分かるリンク名にする
12. **裏付けとなった会議・議録:** 会議名、議案番号、議案名、および議事録からの発言抜粋・詳細ページへのリンク情報

`source_refs` の各要素は `session_id`、`meeting_id`、`meeting_type`、`meeting_title`、`session_label`、`date`、`bill_number`、`bill_name`、`evidence_quote` を持つ。IDは実際の `meetings` / `meeting_sessions` と照合し、確認できない抜粋は作らない。

`decision_date` は議決日、`proposals.published_date` はサイト公開日であり、異なる日付である。新規公開・更新時は既存値と公開機能の設定を確認し、更新日を公開日として上書きしない。
報告・協議だけの記事には架空の議案番号・議案名・議決日を付けない。議案情報がない場合は空欄、議決日は `null` とする。

### 確認から公開まで
1. 既存記事との重複を確認し、原文から暮らしの論点を選ぶ。
2. 1件ずつ全文・出典・未確認事項を提示し、記事とAIインタビューの内容承認を得る。
3. 画面確認を求められたら、本番DBへ先に書かず、独立worktreeのローカルデータで本番と同じカードを表示する。質問一覧だけの確認か、実際のAI会話かを明示する。
4. 段落、全体の情報量、会議名と日付、公式外部リンク、インタビュー導線を確認する。
5. 本番DB書き込みと一般公開は内容承認と区別して承認を得る。共有DBの下書きを安全なプレビューとみなさない。
6. 登録後に両記事テーブルの整合、既存記事が不変であること、公開全文・出典・外部リンク・AIインタビュー設定と動作を確認する。コード変更が必要な表示改善はPR・デプロイが別途必要であり、DB反映だけで完了したと伝えない。

## 4. AIへの依頼プロンプト（実務用テンプレート）
VSCodeなどでAIにトピックス記事の作成を指示する際は、以下のプロンプトをそのままコピーして使用してください。

```markdown
以下の【元となる議事録テキスト・関連議案のデータ】をもとに、「みらいぎかいっち＠大分市」のトピックス記事を作成してください。
DBには登録せず、見出しと本文の全文、出典、未確認事項を先に提示してください。
（※会議全体の要約ではなく、市民の暮らしに直結するテーマを深掘りする市民向け解説記事を作成すること）
中学生レベルの分かりやすさ、生活者目線、「情報は濃く、表現はやわらかく」を守ってください。声は出典のある意見と想定例を区別し、実在の発言を捏造しないでください。
議案の変更点を説明するだけでなく、暮らしの困り事・背景・市の説明・議会の指摘・残る課題を掘り下げてください。既存記事と同程度の分量・具体性を記事全体で確保し、詳細は3〜4段落、ポイントは見出しの後で改行してください。
想定の声は大分弁のセリフ調とし、AI生成の説明はFAQに統一して記事内注記を重ねないでください。全記事にAIインタビューのテーマ・質問・説明資料も用意し、内容確認を受けてください。

【元となる議事録テキスト・関連議案のデータ】
（ここに、記事の根拠となる議事録の該当部分や発言内容、対象の議案情報を貼り付け）

【出力してほしいフォーマット】
以下の構成で出力してください：

## タイトル
（[ステータス] + 【テーマ名】 + キャッチコピー。全体で30文字以内）

## カテゴリ
（子育て・教育 / 安心・安全・防災 / まちづくり・暮らし / まちの仕組み・選挙 から1つ選択）

## 要約（3行）
- 1行目：
- 2行目：
- 3行目：

## 詳細
（経緯や背景を含めた300〜500文字の解説文。空行で3〜4段落に分け、中学生にもわかる表現で）

## 理由・背景
（行政側の意図や背景。200文字以内）

## ポイント3つ
- ポイント1：
- ポイント2：
- ポイント3：

## 対象者
（この決定が直接影響する市民の層）

## 賛成・期待の声
（大分弁のセリフ調の想定例。記事内注記は重ねず、実在人物の発言を捏造しない）

## 慎重・懸念の声
（大分弁のセリフ調の想定例。根拠のない論点は無理に作らない）

## 外部の関連リンク
- 大分市等の公式ページのURL・内容が分かるリンク名
- 一般案内か個別の告知かを区別。PDFは明記

## AIインタビュー（全記事必須）
- 記事ごとのテーマ・質問・深掘り指針
- 説明に用いる確認済みの資料・時点・未確認事項（想定の声を事実として含めない）
- 内容承認後にsource='topic'の受け皿へ設定し、interview_bill_idで紐付ける

## 裏付けとなった会議・議録（source_refs用）
- 会議ID・開催日ID・会議種別：（既存の `meetings` / `meeting_sessions` と照合）
- 会議名：（例：文教常任委員会（3月23日））
- 議案番号・名称：（例：議第35号 大分市学校給食の管理に関する条例の一部改正について）
- 議事録からの抜粋・発言内容：（実際の原文を確認し、未確認なら空欄）

【注意事項】
- 中国語の漢字（议、务、该 等）は一切使用しないこと
- 議事録の情報を省略せず、核心を正確に言語化すること
- 【トピックスと関連リンク】：
  `source_refs` のID・日付・議案情報を実データと照合し、表示できる会議リンクと議案詳細リンクを確認すること。本文の承認、本番DB書き込み、一般公開はそれぞれ確認すること。
  会議リンクは会議名＋年月日で表示すること。報告・協議には架空の議案番号・議決日を付けないこと。公式外部案内は別に確認し、AIインタビューの導線・開始・応答も検証すること。
```
