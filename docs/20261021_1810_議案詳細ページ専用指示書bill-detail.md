# 議案詳細ページ専用指示書bill-detail.md

本書は、「みらいぎかいっち＠大分市」の議案詳細ページ・議案カード（`/committees/bill-pickups/[id]`）を作成・更新する際の個別ルールおよびプロンプトの仕様を定めるものである。作業時は [全体共通ルール](20261021_1800_全体共通ルールmaster-workflow.md) を必ず遵守すること。

## 1. ページの基本仕様
- **【表側】サイト上の場所・役割**
  - **URLパス:** /committees/bill-pickups/[id]
  - **役割:** 予算案や条例改正などの個別の議案について、市民がその内容、背景、重要ポイント、影響を受ける人を深く理解できるように解説するページ。
  - **審議のステータス（ステップバー）:** `bills.status` がある場合、議案上程・委員会審査・本会議採決・結果などの進捗を表示する。
  - **本会議での賛否:** 出典を確認済みの議案では、本文末の「審議結果・出典」の後に、議決対象の正式名・会期・賛否・公式資料へのリンクを表示する。予算の一部施策を紹介するページでは、予算全体への賛否であり、その施策単独の賛否ではないことを明記する。
  - **説明の詳しさ切り替え:** 「説明をもっと詳しく」で `bill_contents` の `normal` / `hard` を切り替える。`## 取り組みの詳細` の本文が切り替え対象で、`hard` がなければ「詳しい説明は準備中です」と表示する。その他の本文は `normal` を表示する。
  - **カードの入口の出どころ（一覧・詳細の上部）:** 大きな見出しは `bill_contents` の標準版（`normal`）の `title`（やさしい言葉の見出し）で、正式な議案名は見出しの下に「正式名称：」として表示する。`title` が無い議案は正式名称を見出しにする。見出しの下の小さな説明文は、**`bill_contents.summary` ではなく**、議事録（`meeting_sessions.bills` の各要素 `number` / `name` / `description` / `result`）の `description` を表示する。`bill_contents.summary` は議案ページのメタ情報などで使われ、議案ピックアップのカードには出ない。
  - **一言説明（`description`）の扱い（現時点の方針）:** この小さな説明文（議事録の議案ごとに約370件）は、**書き直さずに今のまま使う**。議案と議事録のひもづけは議案番号・議案名・年（会期）で決まり、`description` は使われないため、書き直さなくても表示やリンクは壊れない。表示は、カードの小さな文、開催日ページの「審議された議案」の一覧に限られる。やさしい言葉にしたくなった場合は、`description` だけを書き直し、`number` と `name` は変えない（変えるとひもづけが切れる）。同じ議案でも開催日ごとに文が違うことがあり、カードには最初の開催日の文が出る。「来年度」のような読む時期で意味が変わる言い方が残っていても、元の資料で年度を確認できるまでは推測で直さない。
- **【裏側】データベース構造**
  - **登録先テーブル:** 議案の基本情報・審議状態は `bills`、難易度別の説明文は `bill_contents`、出典となる開催日・議案リストは `meetings` / `meeting_sessions`。
  - **由来の区別:** 議案は必ず `bills.source = 'meeting'`（既定値）で登録する。`source = 'topic'` の行はトピックスのAIインタビュー受け皿であり、議案ではない（詳細は master-workflow.md「`bills` テーブルの住み分け」）。
  - **表示条件:** 議事録内の議案と公開済み `bills` を一意に対応付けられる必要がある。詳細本文には `normal` の `bill_contents.content` が必要。`hard` を登録する場合も同じ見出し `## 取り組みの詳細` を使う。
- **【リンク関係の仕組み】**
  - ページ内から、その議案を審議した「各会議（本会議・委員会）の議事録要約ページ」へ相互にリンクが張られる仕組み。
  - 対応する公開中のトピックス用AIインタビューを特定できた場合に導線を表示する。記事やインタビューのリンクが必ず付くと決めつけず、実画面で確認する。
  - カテゴリバッジは関連トピックスの `source_refs` による記事カテゴリと、議案に付いた `bills_tags` のタグ名から導出する。記事がなくても対応するタグで補える。既存の `tags.label` と議案IDを照合し、承認後に `bills_tags` へ紐付ける。
  - 賛否は[公式資料の記録](../web/src/features/committee-minutes/shared/data/bill-vote-snapshots.ts)に、採決時点の会派・議員ごとの結果を保存する。投票者の賛否が会派内で一致した場合のみ会派名にまとめ、分かれた場合と無所属は個人名を表示する。議長・欠席・退席・法律上の除外は賛否と分ける。会派名と現在の議員一覧に掲載されている会派名が一致すれば、その会派の位置にリンクする。同名の会派が現在の一覧にない場合は、その旨を表示し、議員一覧の先頭へリンクする。個人のリンク先は本人と一致する現在の議員紹介。
  - 賛否データは現時点では管理画面やDBから編集できず、新しい議案は公式資料・議案ID・会期・各議員の投票・会派・出典を照合して上記ファイルを更新する。`○` / `×` は賛成 / 反対、`欠` は欠席、`退` は退席、`除` は採決からの除外、`議` は議長の採決不参加を表す。確認内容をユーザーに提示し、公開前の承認を得る。

実装の確認先: [議案詳細の表示](../web/src/features/committee-minutes/server/components/bill-pickup-detail-view.tsx)、[議案ピックアップの組み立て](../web/src/features/committee-minutes/server/loaders/get-bill-pickups.ts)。

## 2. ライティング・ガイドライン（トーン＆マナー）
サイトのコンセプトは「市政を身近にする。難しい政治を分かりやすくする。」。次の「2段階の階層構造」で書く（詳細は[全体共通ルール](20261021_1800_全体共通ルールmaster-workflow.md)「5. 表現の共通ルール」）。
- **入口（議案カードの見出し・一覧の一言説明）:** 専門用語や硬いお役所言葉（「補正」「改正」「措置」など）を一切使わず、**小学生でもパッと見て一瞬でわかる**くらい極限までシンプルにする。「何が／だれに／どうなる」のうち一点に絞る。見出しは `bill_contents.title`、一言説明は `meeting_sessions.bills[].description` を指す（一言説明は現時点では書き直さない方針。1章「一言説明（`description`）の扱い」を参照）。正式な議案名は残し、見出しをやさしい言葉にした場合も正式名称を確認できるようにする。
- **中身（取り組みの詳細・背景・理由・重要ポイント・対象者・審議結果）:** 行政的な背景や情報を削らずに網羅しつつ、**中学生でもちゃんと読めて意味が分かる**よう、専門用語をかみ砕いた丁寧な解説にする。
  - `normal`（標準）: 中学生がそのまま読めて意味が分かる説明。
  - `hard`（詳しい説明）: 行政的な経緯・根拠・数字まで掘り下げて網羅する。専門用語を使う場合は初めて出る場所で言い換えや短い説明を添え、中学生がたどれるようにする。
- **文体:** 読者に語りかける、柔らかく誠実な丁寧語を使用する。
- **生活者目線:** 単なる行政用語の解説にとどめず、「市民の暮らしにどう影響するのか」という視点を重視する。
- **情報の密度と品質（情報の省略禁止）:** 行政が公開している議案の主旨や理由、背景を勝手に削らず正確に言語化する（「情報は濃く、表現はやわらかく」）。入口を簡単にした分の情報は、中身に残す。
- **中国語漢字の排除:** 议、务、该 等の中国語漢字は一切使用しないこと。

## 3. データベース / 項目定義（入力フォーマット）
議案詳細の案は次の項目を議案ごとに整理する。背景・ポイント等は独立したDB列と決めつけず、実際の `bill_contents.content` のMarkdown構成と照合する。

1. **議案種別・番号:** （例：「予算」「法案」などのバッジ ＋ 「令和8年 議第75号」）
2. **議案名:** 正式な議案の名称。複数議案を扱うときは情報が混入しないよう議案ごとに分ける。同一の一般会計予算に複数のテーマがあるときは、議案IDを維持し、必要に応じてサブタイトルで区別する。
3. **審議のステータス:** 現在の進捗段階（議案上程、委員会審査、本会議採決、可決 / 否決 等）
4. **カテゴリタグ:** 子育て・教育、安心・安全・防災、まちづくり・暮らし、まちの仕組み・選挙 から選択（複数可）
5. **簡易概要（入口）:** 一目で内容がわかる短い説明文。小学生でもパッと見て一瞬でわかる言葉にする。議案ピックアップの一覧に出る一言説明は、ここの `bill_contents.summary` ではなく `meeting_sessions.bills[].description`（議案ごとの説明）である。両方を書き直す場合は、同じ意味でそろえる。
6. **関連する議事録一覧:** 審議された本会議・委員会の日付と名称のリンク集
7. **取り組みの詳細（中身）:** 議案の具体的な内容や変更点の詳しい解説。中学生が読めて意味が分かる表現にする。
8. **背景・理由（中身）:** なぜこの議案が必要になったのかの経緯・意図
9. **重要ポイント（中身）:** 核心となるポイントの箇条書き（3点など）
10. **主に影響を受ける人・対象者（中身）:** この決定で直結する市民層や担当部局
11. **審議結果・出典:** 可決・否決などの結果と、根拠となる会議へのリンク
12. **過去情報・ステータス更新:** 新着議事録が既存の議案の審議状況や続報に影響するか確認し、根拠と承認を得て必要な項目を更新する。

AIが作成した本文・状態・出典を先にユーザーへ提示する。本番DBへの書き込みと公開は別途承認を得て、議案ID、会期、表示先、更新件数を照合する。

## 4. AIへの依頼プロンプト（実務用テンプレート）

VSCodeなどでAIに議案詳細データの作成を指示する際は、以下のプロンプトをそのままコピーして使用してください。

```markdown
以下の【議案データ・関連議事録テキスト】をもとに、「みらいぎかいっち＠大分市」の議案詳細ページ用の案を作成してください。DBには登録せず、全文・出典・未確認事項を先に提示してください。
旧みらいぎかいっちのガイドライン（生活者目線、「情報は濃く、表現はやわらかく」）に加え、サイトのコンセプト「市政を身近にする。難しい政治を分かりやすくする。」に沿った次の2段階の階層構造を厳守してください。
- 入口（簡易概要など、カードの表に出る短い説明）：専門用語や硬いお役所言葉を一切使わず、小学生でもパッと見て一瞬でわかるくらい極限までシンプルにする。
- 中身（取り組みの詳細・背景・重要ポイント・対象者など）：行政的な背景や情報を削らずに網羅しつつ、中学生でもちゃんと読めて意味が分かるよう、専門用語をかみ砕いた丁寧な解説にする。

【議案の基本情報】
- 種別・議案番号：（例：予算 / 令和8年 議第75号）
- 議案名：（例：令和8年度大分市一般会計補正予算（第1号））
- 現在の審議ステータス：（例：可決 / 否決、委員会審査中 など）
- カテゴリ：（子育て・教育 / 安心・安全・防災 / まちづくり・暮らし / まちの仕組み・選挙 から選択）

【元となる議案資料・議事録テキスト】
（ここに議案の提案理由書や関連議事録のテキストを貼り付け）

【出力してほしいフォーマット】
以下の構成（画面の表示順）で出力してください：

## 審議のステータス
- 現在の段階：（例：可決 / 否決 まで完了 など、ステップバー表示に反映する状態）

## 簡易概要（入口）
（小学生でもパッと見て一瞬でわかる、やさしい言葉の2〜3文。専門用語は使わない。意味・数字・結論を変えない）

## 取り組みの詳細（中身）
（議案の具体的な内容や変更点を、中学生がちゃんと読めて意味が分かるように解説した文章。専門用語は初めて出る場所で言い換えを添える）

## 背景・理由（中身）
（なぜこの議案が必要になったのかの経緯・意図。行政的な背景は削らず、かみ砕いて書く）

## 重要ポイント
- ポイント1：
- ポイント2：
- ポイント3：

## 主な影響を受ける人・対象者
（直接影響を受ける市民の層や関係部署）

## 審議結果・出典
- 議決結果：（例：令和8年6月26日の本会議で原案可決。）
- 関連会議へのリンク情報：（例：6月23日・建設常任委員会、6月26日・本会議）

【注意事項】
- 本文は `bill_contents.content` 用のMarkdownとし、切り替え対象の見出しを正確に `## 取り組みの詳細` とする。`normal` と、必要な場合の `hard` を区別すること
- 議案の基本情報・審議状態と本文、会議の議案リストを混同しないこと
- 中国語の漢字（议/务/该 等）は一切使用しないこと
- 議案の情報を省略せず、核心を正確に言語化すること
- 入口は小学生でも一瞬でわかる言葉、中身は中学生が読めて意味が分かる丁寧な解説にすること。入口を簡単にして意味・数字・結論を変えず、正式な議案名は残すこと
- `hard` を作る場合は、`normal` より行政的な経緯・根拠を詳しくしつつ、専門用語には初出で言い換えを添えること
- 市民の暮らしにどう影響するのかという生活者目線を意識すること
```
