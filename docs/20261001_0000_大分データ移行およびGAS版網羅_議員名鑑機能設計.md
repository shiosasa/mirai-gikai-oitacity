# 大分データ移行・GAS版要素網羅・議員名鑑の実装計画

## 目的と前提
「みらいぎかいっち」の大分版について、福岡のテストデータから大分の一次資料に基づくデータへ切り替え、GAS版独自の表現・対話体験を引き継ぎ、議員名鑑を追加する。ここではDB変更、データ移行、画面実装、検証の順とサンプルを定める。

実装前に、対象が「大分市議会」なのか「大分県議会」なのか、または別の自治体なのかを確定する。自治体名・議員・会派・会期・議案を推測で登録しない。以下のseed例は既存データを再利用する設計例であり、実際の大分データは議会の公式資料と照合して別途作成する。

### 現行コードで確認したこと
- `packages/seed/main/data.ts` には福岡県議会の会期・会派・議案がある。タグには大分市議会向けカテゴリーが混在しており、seed全体を大分版と見なせない。
- `packages/seed/main/run.ts` は先頭で `clearAllData()` を呼び出す。その関数は議員、議案、議案内容、会期、タグ、会派、委員会、AI対話・レポートなどを削除する。環境変数の接続先に対して実行されるため、本番で `pnpm seed` を実行してはならない。
- `bills.source_url` と `bills.discussion_overview_points` はmigrationで追加済み。`council_sessions` には開始日とnullableな終了日がある。`tags` / `bills_tags` も既存。
- 型生成ファイルには旧形式の `politicians`（単一 `faction_id` と `committee_names` 配列）が現れるが、追跡中のmigrationには作成定義が見つからない。DBとmigration履歴がずれている可能性があるため、既存テーブルの定義・本番migration履歴を照合してから変更する。
- `bill_contents` には `title`、`summary`、`content` がある。必要理由・対象者・争点を既存カラムとして扱わず、拡張が必要。

## 実施順序
1. **範囲・データソース確定**: 対象議会を確定し、GAS版のシート・列・文言・URL・既存データをエクスポートして対応表を作る。
2. **バックアップと現状棚卸し**: Supabaseプロジェクト名とURLを機密値を表示せず照合し、テーブル件数・福岡データのID・AI対話履歴等の保持要否を記録。復元手順を確認する。
3. **DB migration**: ローカルSupabaseで適用し、制約・RLS・型生成・テストを確認する。
4. **大分データの作成・検証**: 公式ソースURL付きデータをstagingへ投入し、件数・リンク・日付・文字品質を照合する。
5. **本番移行**: 承認済みの削除対象IDに限定して、バックアップ確認後に移行する。新規データの投入と削除を同じレビュー済み手順で行い、画面で確認する。
6. **UI・AI・議員名鑑**: 既存のfeature構成、議案コンテンツ、インタビュー機能を再利用して順次実装する。

**本番データ変更は別途ユーザー承認を得てから行う。** この設計作成ではDB接続・削除・migration適用は実行しない。

## 1. Supabase変更案

### 1.1 議員マスタと所属履歴
議員の所属は複数・時期変更に対応できるよう中間テーブルで保持する。旧 `faction_id` / `committee_names` は互換移行が完了するまで残し、画面の正規ソースは所属テーブルにする。写真はSupabase Storage等の公開URL、連絡先は本人が公開を認めた情報だけ登録する。

次のSQLは、既存 `politicians` テーブルが型生成に現れる旧形式であることを確認した後の案。テーブルが存在しない場合は同名の土台テーブルを作成できるが、既存テーブルが異なる場合はDDLをそのまま適用せず、実スキーマに合わせてmigrationを調整する。

```sql
-- supabase/migrations/<timestamp>_add_politician_directory.sql
create table if not exists public.politicians (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  name_kana text,
  avatar_url text,
  terms_count integer not null default 1 check (terms_count >= 0),
  bio text,
  website_url text,
  twitter_url text,
  contact_info text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

-- 既存の型定義にある旧テーブルでも、追加列だけ補えるようにする。
alter table public.politicians
  add column if not exists name_kana text,
  add column if not exists avatar_url text,
  add column if not exists terms_count integer not null default 1,
  add column if not exists bio text,
  add column if not exists website_url text,
  add column if not exists twitter_url text,
  add column if not exists contact_info text,
  add column if not exists updated_at timestamptz not null default now();

create table if not exists public.politician_factions (
  id uuid primary key default gen_random_uuid(),
  politician_id uuid not null references public.politicians(id) on delete cascade,
  faction_id uuid not null references public.factions(id) on delete restrict,
  started_on date,
  ended_on date,
  source_url text,
  created_at timestamptz not null default now(),
  check (ended_on is null or started_on is null or ended_on >= started_on)
);
create unique index if not exists politician_factions_one_current
  on public.politician_factions (politician_id) where ended_on is null;

create table if not exists public.politician_committees (
  id uuid primary key default gen_random_uuid(),
  politician_id uuid not null references public.politicians(id) on delete cascade,
  committee_id uuid not null references public.committees(id) on delete restrict,
  started_on date,
  ended_on date,
  source_url text,
  created_at timestamptz not null default now(),
  check (ended_on is null or started_on is null or ended_on >= started_on),
  unique (politician_id, committee_id, started_on)
);

alter table public.politicians enable row level security;
alter table public.politician_factions enable row level security;
alter table public.politician_committees enable row level security;

create index if not exists politician_factions_faction_id_idx
  on public.politician_factions (faction_id);
create index if not exists politician_committees_committee_id_idx
  on public.politician_committees (committee_id);
```

既存 `politicians.faction_id` と `committee_names` の値を中間テーブルへ移す処理は、会派名・委員会名の正規化対応表を用意してから別migrationまたは一回限りの移行スクリプトで行う。名称一致だけで黙って紐付けず、未解決行を出力して手動確認する。`name_kana` を既存行でNULL不可にできるかも投入前に検証する。

### 1.2 議案カード・根拠・発言者連携
- 3行要約は既存の `bills.discussion_overview_points text[]` を使う。最大3件・空要素なしをseed検証で保証する。
- カテゴリーは既存 `tags` / `bills_tags` を使う。4タブはタグラベルで絞る。
- `bills.source_url` は議案の一次資料リンクに使う。一般質問には既に `general_questions.source_url` がある。議案質疑の出典と議員紐付けは `bill_discussions` に追加する。
- 詳細欄を構造化し、追記を日付付きタイムラインで保存する。

```sql
alter table public.bill_contents
  add column if not exists reasons text,
  add column if not exists key_points text[] not null default '{}',
  add column if not exists target_audience text[] not null default '{}',
  add column if not exists supporting_arguments jsonb not null default '[]'::jsonb,
  add column if not exists cautious_arguments jsonb not null default '[]'::jsonb,
  add column if not exists updates jsonb not null default '[]'::jsonb;

alter table public.bill_contents
  add constraint bill_contents_arguments_are_arrays
    check (
      jsonb_typeof(supporting_arguments) = 'array'
      and jsonb_typeof(cautious_arguments) = 'array'
      and jsonb_typeof(updates) = 'array'
    );

alter table public.bill_discussions
  add column if not exists politician_id uuid
    references public.politicians(id) on delete set null,
  add column if not exists source_url text;

create index if not exists bill_discussions_politician_id_idx
  on public.bill_discussions (politician_id);
```

`bill_contents` への制約追加は既存JSON値が配列であることを先に確認し、既に制約名が存在するDBには重複作成しないmigrationにする。争点JSONの1項目は `{ "text": "...", "source_url": "..." }` を基本形とし、事実確認できない「賛成派・慎重派」の見解を創作しない。更新履歴は `{ "date": "YYYY-MM-DD", "text": "...", "source_url": "..." }` とする。

全テーブルでRLSを有効にし、リポジトリ方針どおりポリシーは作らない。読み書きはサーバー側の `createAdminClient()` を通し、Service Role Keyをブラウザーへ渡さない。migration適用後にSupabase型を再生成し、既存の `faction_stances` など似たデータとの責務重複を確認する。

## 2. 福岡から大分へのデータ移行

### 2.1 移行対象の確定
「福岡データ」全削除の前に、GAS/seed/本番DBのそれぞれでデータセットと保持要否を表にする。少なくとも会期、議案、議案内容、タグ関連、会派見解、委員会・議事録、議員、一般質問、インタビュー設定・質問・セッション・メッセージ・レポートを棚卸しする。管理ユーザー、認証データ、監査上必要なログなどは一括削除対象に含めない。

**`pnpm seed` は移行コマンドではない。** 現在のseedは `clearAllData()` で複数テーブルを削除後、デモ用インタビューを含む全seedを投入する。本番URLが設定されている環境で絶対に実行しない。また `clearAllData()` は削除エラーを十分に検査しないため、そのまま本番移行に流用しない。

### 2.2 安全な移行手順
1. `.env.production` の接続先を秘密値を表示せず確認し、Supabaseのプロジェクト名が大分版であることを確認する。別地域クローンの環境変数を使わない。
2. Supabaseのバックアップ/PITRと復元手順を確認し、移行前の各テーブル件数・既存レコードIDを保存する。
3. 公式資料から大分用データを作成し、全レコードに一次資料URLを付ける。議員・会派・委員会・会期は対応表でIDを解決する。
4. stagingへ投入する。外部キー・一意制約・参照URL・日付・議決状態・要約3件を検証し、旧福岡データが混ざっていないことを確認する。
5. 本番の削除対象を**承認済みのIDリスト**に限定し、対象件数が想定件数と一致することをdry-runで確認する。親子テーブルの削除順、保持対象、FK cascadeをレビューしてから実行する。
6. 大分データを投入し、主要ページと発言者リンクを確認後、移行前後の件数・URL・画面を照合する。

現行スキーマに自治体ID/地域IDがないため、地域名に基づいた安全な `DELETE` 条件は書けない。根拠のない `TRUNCATE` や全行 `DELETE` は使わない。将来1つのDBで複数自治体を運営する場合は、`councils` マスタと各地域データの `council_id` を追加してテナント境界を明示する。現在の地域別プロジェクト構成で大分版だけを置き換えるなら、既存全件を消す方式ではなく、棚卸ししたデータ所有範囲のIDに限って処理する。

投入データの最低限の検証例（seed側でDB送信前に実行する）：

```ts
function validateBillSeed(bill: {
  name: string;
  source_url: string | null;
  discussion_overview_points: string[];
}) {
  if (!bill.name.trim()) throw new Error("議案名が空です");
  if (!bill.source_url) throw new Error(`${bill.name}: 出典URLがありません`);
  if (bill.discussion_overview_points.length !== 3) {
    throw new Error(`${bill.name}: 3行要約は3件必要です`);
  }
  if (bill.discussion_overview_points.some((point) => !point.trim())) {
    throw new Error(`${bill.name}: 要約に空行があります`);
  }
}
```

## 3. フロントエンドとGAS版の引き継ぎ

### 3.1 トンマナ
- メッセージ: 「おおいたん市議会いま何しよん？」「むずかしい議会をわかりやすく。」
- `Noto Sans JP` をアプリのフォント設定で読み込み、色は要望の `#d97792` / `#fff5f7` / `#ebdbe0` をデザイントークンとして定義する。Tailwindに直接カラーコードを書かず、`globals.css` のテーマトークンを介して参照する。
- 「非公式の市民向け情報整理」であることを明示し、議会の公式情報源へリンクする。議会の公式見解とサービスの要約を混同させない。

### 3.2 会期ステータス
`is_active` だけで表示を決めず、JSTの日付と `start_date` / `end_date` を主判定に使う。`is_active` は管理画面での注目会期指定に限定する。`end_date` がNULLの会期は開始日以降を会期中として扱う。次回が未定の場合の表示も実装する。

```ts
type CouncilSession = {
  name: string;
  start_date: string;
  end_date: string | null;
};

type SessionStatus =
  | { kind: "active"; session: CouncilSession }
  | { kind: "upcoming"; session: CouncilSession }
  | { kind: "undetermined" };

export function resolveSessionStatus(
  sessions: CouncilSession[],
  todayJst: string
): SessionStatus {
  const active = sessions.find(
    (session) =>
      session.start_date <= todayJst &&
      (session.end_date === null || todayJst <= session.end_date)
  );
  if (active) return { kind: "active", session: active };

  const upcoming = sessions
    .filter((session) => session.start_date > todayJst)
    .sort((left, right) => left.start_date.localeCompare(right.start_date))[0];
  return upcoming ? { kind: "upcoming", session: upcoming } : { kind: "undetermined" };
}
```

日付文字列は `YYYY-MM-DD` に揃え、`todayJst` はサーバー側で `Asia/Tokyo` の暦日として作る。会期中は「会期中（○月○日〜○月○日）」、終了日が未定なら「会期中（○月○日〜）」、次回があれば「閉会中（次回 ○月○日〜）」、なければ「閉会中（次回定例会未定）」とする。複数会期が重なる異常データはseed検証でエラーにする。

### 3.3 議案カードとカテゴリーフィルター
カードには、カテゴリ・進行ステータス・議決日・公開日・更新日、タイトル、3点要約、詳細、必要な理由、重要ポイント、対象者、根拠リンクを表示する。更新は `[追記:YYYY/MM/DD]` を含む時系列として表示。推進・慎重の比較欄は出典付きのJSONデータがある場合のみ表示する。

詳細はネイティブの `<details>/<summary>` または既存Disclosure UIを使用し、キーボード操作・展開状態を支援する。ボタンはリポジトリ規約に従い `@/components/ui/button` を使う。AI起動ラベルは「💬 これ、どう思う？話してみらん？」とし、対象議案IDを既存インタビュー作成処理へ渡す。

カテゴリータブは `すべて`、`子育て・教育`、`安心・安全・防災`、`まちづくり・暮らし`、`まちの仕組み・選挙`。タグをjoinした議案を読み込み、選択ラベルで絞る。該当0件の状態も表示する。

```ts
const visibleBills =
  selectedCategory === "すべて"
    ? bills
    : bills.filter((bill) =>
        bill.tags.some((tag) => tag.label === selectedCategory)
      );
```

カードのセクション順は「何が変わる？」「なぜ必要？」「大事なポイント」「影響を受ける人」「議論で出た意見」「根拠資料」とし、情報がない項目は空欄の枠を出さない。

### 3.4 聞き役AIインタビュー
既存の interview config/session/message/report とAI生成経路を再利用し、議案ごとの二重実装を避ける。開始時にニックネームを尋ね、本名・住所・連絡先などを書かない注意を表示する。終了・途中で閉じる場合は、会話保存の有無と扱いを明示し、同意した会話のみ既存の保存フローへ渡す。個人情報をモデル入力・保存しないよう既存の同意・保持方針を確認する。

```text
あなたは議会の議案について市民の声を聞く聞き役です。
評価、説得、賛否への誘導をせず、相手の考えを尊重してください。
まず短く共感し、その後に深掘りする質問を1つだけ返してください。
質問を複数並べたり、回答を急かしたりしないでください。
自然な大分・九州の言葉を控えめに交えます（「〜しよん？」「〜な」など）。
方言を誇張せず、事実を尋ねられたら議案資料の根拠を示し、不明点は不明と伝えてください。
個人を特定する情報を求めないでください。
```

## 4. 議員名鑑ページ
- URL案: `/politicians`（一覧）、`/politicians/[id]`（詳細）。ページは薄いルートにし、データ取得と表示を既存feature構成に配置する。
- 一覧・詳細: 顔写真、氏名、ふりがな、期数、現所属会派、委員会、公開を許可されたリンク・連絡先、一言コメント。未登録の値は非表示にする。
- 所属履歴と根拠URLを記録する。期数は確認した基準日を運用データに残すか、任期履歴から算出できる設計にする。
- `bill_discussions.politician_id` を解決できた発言者名に設定し、発言者名からプロフィールへリンクする。表記揺れは氏名文字列の自動一致だけで確定しない。未解決はNULLのまま管理画面で確認する。
- 議員一覧の順序、同姓同名、退任議員の表示、写真の権利・本人確認、連絡先公開の同意を受け入れ条件に含める。

## 要確認事項
1. 対象は大分市議会か、大分県議会か、別の自治体か。
2. 本番の福岡データは全消去か、一般質問・インタビュー記録など一部を保持するか。
3. GAS版のエクスポート、公式ソース一覧、議員写真・連絡先の公開許諾を誰が提供・確認するか。
4. AI対話ログを保存する場合の同意文言・保持期間・削除方法。
