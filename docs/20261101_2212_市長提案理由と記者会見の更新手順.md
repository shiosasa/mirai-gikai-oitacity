# 大分市長の提案理由・記者会見 更新手順

市長紹介ページに載せる、定例会などの提案理由の要約と記者会見の発表・質疑を定期的に更新するための手順です。2026年11月1日時点の実装に基づきます。作業時は最新のコード・公式情報・DBの状態を再確認してください。

## はじめに

- 対象画面は [市長紹介](https://mirai-gikai-oitacity-web.vercel.app/politicians/mayor)、[記者会見一覧](https://mirai-gikai-oitacity-web.vercel.app/press-conferences) と各会見の詳細ページです。
- 管理画面の「information」はお知らせ用です。管理画面再編版では「市長提案理由」「記者会見」から編集できます（[管理画面の設計・運用](20261103_0100_大分市版管理画面再編設計.md)）。再編版のデプロイ前は従来のデータ更新手順を使います。いずれの場合も下記の確認・承認は必要です。
- DBの接続先・認証は [DB接続規約](../.claude/skills/db-access/SKILL.md) と現在の環境を照合します。既存手順に他地域や古い接続先の記載がある場合は、そのまま使用せず確認します。ローカル画面、Vercelプレビュー、本番が同じ本番DBを参照する場合があります。
- **AIが作成・修正した全文をユーザーに提示し、内容の承認を得る前にDBへ登録しません。** 内容の承認、本番DBへの書き込みの許可、一般公開の許可は別々に確認します。下書きの登録も本番DBへの書き込みです。
- 既存データを消して入れ直さず、対象を特定して必要な項目だけ更新します。意図しない差分・重複・途中失敗があれば止め、現在の保存状態を読み直してから対応を相談します。

### AIへの依頼例

> ○年第○回定例会の市長提案理由を更新したいです。大分市の公式原文を確認し、DBに登録する前に要約案と出典を見せてください。

> ○年○月の市長記者会見を追加したいです。公式資料と動画を確認し、発表と確認できる質疑の要約案を見せてください。登録・公開は私の確認後にしてください。

## データの対応

| 対象 | 保存先 | 表示と注意 |
|---|---|---|
| 定例会などの提案理由 | `meetings.mayor_proposal_text`、`mayor_proposal_summary`、`mayor_proposal_source_url` | 提案理由の原文が空でない会議だけが対象。画面には要約と公式原文へのリンクを表示し、原文自体は表示しない |
| 会見の基本情報 | `press_conferences` の `slug`、`title`、`held_at`、`youtube_url`、`status` | 通常画面は `published` のみ表示。`slug` は一意で、既存のURLに使われる |
| 会見の発表・質疑 | `press_conference_items` の `press_conference_id`、`item_type`、`order_index`、`title`、`summary`、`material_url` | `item_type` は発表が `announcement`、質疑が `qa`。`material_url` は1項目につき1件 |
| 発言のやりとり | `press_conference_turns` | 確認できたやりとりがある場合のみ登録。要約だけなら無理に作らない |

提案理由に下書き用の状態はありません。本番DBの `meetings` を更新すると、共有DBを読む本番の市長紹介ページにも反映され得ます。すでに公開中の会見の項目を編集する場合も同様です。公開前に画面を確認したいときは、別DBや画面用の仮データで確認し、共有DBに先に書き込まないでください。

## 1. 対象と公式資料を確認する

1. 対象となる定例会・会見の日付、既存データの有無、更新したい範囲を確認します。会議や会見のID・日付・見出し・状態を読み取り、既存レコードと取り違えないでください。
2. 提案理由は [大分市公式「市議会提案理由」](https://www.city.oita.oita.jp/shisejoho/kekakuzaise/shinozaise/teanriyu/index.html) から対象会期の原文を探し、その会期の個別URLを控えます。議事録にある実際の会議名・日付とも照合します。
3. 会見は [大分市公式「記者会見」](https://www.city.oita.oita.jp/shisejoho/shichoshitsu/kishakaiken/index.html) から対象回を探し、発表項目、各配付資料PDF、公式動画を確認します。年度・月からURLを推測せず、実際のリンク先を開きます。
4. 発表事項は公式ページ・資料を一次情報とします。質疑は会見の動画・公式書き起こしなどで実際の発言を確認します。自動字幕だけの場合は誤認識や話者混同に注意し、可能な限り音声と照合してください。照合できなければその旨をユーザーに明示します。
5. 動画や質疑を確認できなければ、推測で補わず未登録・準備中とします。PDFの内容を、確認していない記者の質問や市長の回答として扱いません。

公式会見ページ自体のURLを入れる専用列は、現行の `press_conferences` にはありません。レビュー時には各回の公式ページURLと資料・動画の対応を提示し、存在しない列や推測したURLを登録しないでください。

## 2. 要約を作成し、内容の承認を得る

### 提案理由

- 会期ごとに、提案された予算・条例・主要施策などを、元の説明に沿って分野別に整理します。提案段階の内容を「決定済み」「実施済み」と断定しません。
- 金額、年度、対象者、事業の名称、条例案と報告事項の違いを原文と照合します。複数会期の内容を混ぜないでください。
- 市民向けの自然な日本語で、必要な分野ごとに見出しを付けます。画面ではプレーンテキストの改行が表示されるため、Markdownの `**` や見出し記号には頼りません。
- 原文は公式サイトへリンクし、画面本文に丸ごと再掲しません。検索条件に使われるDBの `mayor_proposal_text` は、公式原文と会議の対応を確認して保持します。表示させるためだけのダミー文字列は入れません。

### 記者会見

- 発表事項は公式の項目・資料に対応させ、見出しと要約を作ります。質疑も確認できた内容だけを、質問と回答の趣旨・話者が分かる形に要約します。代表例の抜粋なら網羅的な記録だと誤解されないようにします。
- 発表資料を登録する場合は、該当する発表項目の `material_url` に確認済みのPDF等の絶対URLを入れます。1項目に複数の資料がある場合は、実際に別の発表項目として分けられるか確認し、無理に重複項目を作りません。表現できない資料があればユーザーに報告します。
- 動画は実際に対象会見のものか確認します。表示に使える形式は `https://www.youtube.com/watch?v=動画ID`、`youtu.be`、YouTubeの埋め込みURLです。`/live/` 形式は動画IDを確認して `watch?v=` 形式に直します。確認できない場合は `youtube_url` を空のままにします。
- `press_conference_turns` を使う場合、DB上の `speaker` は市長が既存の `governor`、記者が `reporter`、担当課などが `secretariat` です。画面では `governor` が「市長」と表示されます。担当課名は `speaker_name` に入れ、他の話者へまとめません。実際に確認できない発言は作りません。

### ユーザーへ提示する内容

更新対象の会期・会見ごとに、**実際に登録する見出しと要約全文**、公式ページ・各PDF・動画との対応、未確認箇所を示します。次を自己確認し、疑問点や音声未照合の有無も伝えてください。

- 数字・日付・固有名詞・提案／決定の区別が公式資料と一致している。
- 会期や会見の項目をまたいだ情報混入、話者・担当課の取り違えがない。
- 語尾・助詞が自然で、中国語の簡体字・繁体字が混入していない。
- 提案理由の原文リンク、発表項目とPDF、質疑と動画の対応を確認した。
- 動画・質疑・資料の未確認や未登録を「準備中」として明記した。

修正依頼があれば差分を反映し、変更後の全文を再確認してもらいます。「要約OK」は内容の承認であり、本番DBへの登録や会見の公開まで自動的に許可されたことにはしません。

## 3. 登録前の確認とDB更新

1. `db-access` を確認し、実際の接続先が大分市版であることを照合して対象レコードの現在値を読み取ります。接続先を特定できない場合は作業を停止します。データ更新の内容・件数・影響範囲を提示し、**本番DBへの書き込みを明示的に承認**してもらいます。
2. 提案理由は対象の `meetings.id`、会議名、日付、現在の原文・要約・公式URLを照合し、承認されたフィールドだけを更新します。会議自体が未登録なら、既存の会議・議事録の登録手順と整合を確認してから進め、IDを推測しません。
3. 新しい会見は既存の `slug`・日付を確認して重複を避け、親 `press_conferences` を `draft` として作成し、そのIDを使って承認済みの `press_conference_items` を登録します。既存の `slug` は変更しません。同月に複数回ある場合も一意の `slug` を確認します。
4. 発表・質疑は同じ会見内で `order_index` を確認し、既存項目の更新では項目ID・種別・現在値まで照合します。`press_conference_items` に重複防止の一意制約があると決めつけず、再送前に保存状態を確認してください。
5. 各書き込みの対象件数を確認し、DBから読み直した値を承認済みの全文・リンク・順序と突き合わせます。想定外の件数や通信エラーがあれば停止し、削除や盲目的な再送はしません。

`press_conferences.updated_at` は子項目の変更を必ず検出する仕組みではありません。公開前の差分確認を親のタイムスタンプだけに頼らず、子項目・資料・動画を含めて再照合します。

## 4. 会見の下書きをローカルで確認する

本番DBへの下書き登録が承認済みなら、ローカル限定の確認画面に `draft` を表示できます。通常のVercelプレビューでは表示されません。下書きは `/politicians/mayor` に表示されますが、一般の `/press-conferences` 一覧・詳細は公開済みだけを取得します。

1. 空きポートを選び、起動環境が正しいDBを参照することを値を表示せずに確認します。既存の環境変数がenvファイルより優先されることにも注意します。
2. ローカルの開発プロセスで `NODE_ENV=development`、`MAYOR_LOCAL_DRAFT_PREVIEW=1` とし、`VERCEL` と `VERCEL_ENV` が設定されていないことを確認します。`review` 等の状態はこのプレビュー対象ではありません。
3. 例えば新しいWindows PowerShellで、接続先を確認済みのenvファイルを指定し、`127.0.0.1` のみにバインドして起動します。パスとポートは実際の環境に合わせて置き換えてください。

   ```powershell
   $env:NODE_ENV = "development"
   $env:MAYOR_LOCAL_DRAFT_PREVIEW = "1"
   if ($env:VERCEL -or $env:VERCEL_ENV) { throw "Vercel環境では下書き表示できません" }
   pnpm exec dotenv -e '<確認済みenvファイルの絶対パス>' -- pnpm --filter web exec next dev --turbopack --hostname 127.0.0.1 --port 3015
   ```

4. `http://127.0.0.1:3015/politicians/mayor` にローカル確認用の注意書きと対象の「下書き」が表示されることを確認します。表示されない場合は接続先・環境変数・状態を調べ、公開状態を変えて代用しません。ユーザーによる確認が終わったら、この作業で起動したサーバーだけを停止し、使用したPowerShellを閉じます。

## 5. 公開と最終確認

1. 下書きの確認後、公開する会見・内容・公開先を提示し、**一般公開の明示的な承認**を得ます。会見を `published` にすると市長ページだけでなく記者会見一覧・詳細にも反映され得ます。
2. 公開直前に `slug`、会見ID、`draft` 状態、承認済みの親・子データを読み直します。対象IDと期待する状態を条件に、その会見だけを `published` に変更し、更新件数が想定と異なれば停止します。公開中の既存会見を確認目的で非公開にしません。
3. DBから親・子の値と状態を再取得し、市長ページ、会見一覧、会見詳細を開いて日付、要約、展開、PDF、動画、準備中表示を確認します。リンク先や動画の再生を確認できなかった場合は、未確認として報告します。
4. 市長詳細は動的表示です。データだけの更新で直ちに再デプロイが必要とは限りませんが、会見一覧・詳細の実際の表示も確認し、反映されなければキャッシュやデプロイ状態を調査します。コード・設定やスキーマの変更を伴う場合は、大分市版の現在の公開先と反映手順を確認して進めます。

参考：2026年11月1日の作業では、1〜10月の会見10件を内容確認後に公開しました。その時点の一部の質疑は自動字幕由来で、音声照合は未実施でした。以降の更新時に同じ件数・状態を前提とせず、既存データと確認状況を再確認してください。
